How I cut regression time by 50%

Rebuilding a 500+ case regression suite for a government-utility platform with Python, Pytest, Page Objects and Selenium Grid, and making it a routine part of every release.

Sudipta Mohanty · SDET · 7 min read

The product code and internal systems are under NDA, so internal details here are simplified. The approach, decisions and results are real.

Context

At Iskraemeco I test Anantya HES/MDM, a web platform used by government utilities to manage smart-meter data. It is database-heavy, has many screens and workflows, and releases have to be safe, because the people relying on it are utility operators and, behind them, billing.

I work in a small team where every engineer owns their area end to end. I led a team of 4, and regression was squarely our responsibility.

The problem

The regression suite had grown past 500 test cases. Running it was slow, and it was the step that held up every release. A slow regression causes three problems:

  • It runs less often. When a full run is expensive, teams start running partial suites and hoping for the best.
  • Feedback arrives late. A defect found at the end of a long run is found days after the change that caused it.
  • Coverage gets uneven. Running across every supported browser multiplies the cost, so cross-browser checks are the first thing to get skipped.

Goals

  1. Make full regression meaningfully faster, without dropping test cases.
  2. Run the same suite on Chrome, Firefox and Edge.
  3. Make tests cheap to maintain when the UI changes.
  4. Make results easy to read for people who don't write tests.
  5. Run it from the CI pipeline, not from someone's laptop.

Architecture

The framework is built in Python with Pytest and Selenium WebDriver. Each layer has one job:

  • Test data lives outside the tests (data-driven testing), so one test function covers many input combinations.
  • Pytest handles fixtures, setup and teardown, markers for suites (smoke, sanity, regression) and parallel execution.
  • Page Objects (POM) hold every locator and page action. Tests describe behaviour, and pages describe the UI.
  • Selenium Grid (hub and nodes) runs sessions in parallel across Chrome, Firefox and Edge.
  • Allure turns results into a report with history, steps and failure screenshots that anyone can read.
  • Azure DevOps YAML pipelines on self-hosted agents run the suite and publish the report.

Results

Full regression now takes half the time it did, with the same 500+ cases and cross-browser coverage on Chrome, Firefox and Edge. Because results land in an Allure report attached to the pipeline run, the conversation after a run is about what failed, not whether anyone ran it.

What I'd do differently, and what came next

Speed was only half the battle. Once regression was fast, the next bottleneck was triage: someone still had to look at every red test and decide whether it was a real bug, a UI change, a flaky environment or bad test data. That's what led to the next generation of the framework:

  • Playwright instead of Selenium for the newer web client, with auto-waiting (no hard sleeps) and runs on Chrome, Edge, Firefox and WebKit.
  • Session capture and replay to get past a server-side login CAPTCHA without false auth failures. How it works →
  • Automatic failure classification with screenshots, traces and video attached, so the defect register holds only real findings. How it works →
  • Requirement traceability: tests are tagged to requirements, so coverage gaps are visible.
  • Claude multi-agent workflows for test generation, triage and reporting. How it works →

If I started again, I'd design for triage from day one: classify failures and attach evidence before optimising for raw speed. A fast suite whose failures nobody trusts is still a bottleneck.
