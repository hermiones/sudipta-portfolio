Fan-out, fan-in: how I use multiple Claude agents for QA

One big prompt that does everything gives shallow results. Splitting QA work across focused agents, then merging their output, works far better.

Sudipta Mohanty · SDET · 5 min read

The idea

Fan-out, fan-in is a simple pattern. An orchestrator takes a task, splits it into independent pieces, hands each piece to a specialist agent working in parallel (fan-out), then collects and merges the results into one answer (fan-in).

I use this pattern with Claude for three repetitive parts of QA: test-case generation, defect triage and QA reporting, across the product lines I test at Iskraemeco. The scripts around it were developed with Cursor AI.

              ┌─► planner   ── scenarios from the requirement
              ├─► test-gen  ── test cases in our format
orchestrator ─┼─► triage    ── classify failures from the run
              └─► reporter  ── summary for the release
                     │
              fan-in ▼  merge · de-duplicate · human review

Why split the work?

  • Focus beats breadth. An agent asked only to find edge cases for one requirement does that job much better than one asked to "test this feature".
  • Parallel is faster. Independent pieces don't wait on each other.
  • Easier to check. Small, specific outputs are quicker for a human to review than one long answer.
  • Easier to improve. If triage is weak, I fix the triage agent's instructions without touching the others.

What each agent does

Test generation

Given a requirement, the agent proposes scenarios: the happy path, boundary values, invalid input and permission cases. The output uses the same structure as our existing test cases, so it slots into the suite instead of becoming a separate document.

Defect triage

Given a failed run (error, logs, screenshot description), the agent proposes a category and a one-line reason. This sits on top of the rule-based classification I describe in classifying test failures.

Reporting

Given the run results, the agent writes a short QA summary for the release: what passed, what failed, what's blocked and what needs a decision.

Where the human stays in the loop

Agents draft; people decide. Nothing an agent produces goes into the suite, the defect register or a release report without a review.

The fan-in step is where that happens. Results are merged and de-duplicated, then reviewed. Generated tests still go through PR review, and triage suggestions are confirmed before a defect is raised.

Results

−40%Manual QA overhead per sprint
−40%Sprint defect escape rate

The time saved goes back into the work that needs judgement: exploratory testing, risk analysis and reviewing what matters.

What I've learned

  • Give each agent one job and a fixed output format. Structured output is far easier to merge and review.
  • Feed real context. Requirements, existing test cases and past defects make the output specific instead of generic.
  • Measure it like any other process change. If it doesn't reduce effort or escaped defects, it's a demo, not a tool.
